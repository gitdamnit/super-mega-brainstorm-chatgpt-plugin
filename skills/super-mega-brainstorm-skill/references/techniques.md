# Technique Engine: choose lenses, don't accumulate rituals

This reference is **complete local operational guidance**, not a list of websites. Use the minimum combination that makes genuinely new options visible. Never imply every lens has been applied if it has not.

## Router

| Situation | First lens | Complement | Why |
|---|---|---|---|
| User articulates feature, not need | Jobs-to-be-Done + How Might We | Five Whys, counterframe | Prevent solution lock-in |
| Same variations keep recurring | SCAMPER | reversal, provocative impossibility | Structural departures |
| Small constrained design space | morphological matrix | elimination, Pareto frontier | Systematic combinations |
| Technical contradiction | TRIZ-style contradiction | first principles + separation in time/space | Make tradeoffs explicit |
| Many stakeholders | Six Thinking Hats | role council + ethics mapping | Separate viewpoints |
| Research/science hypothesis | abduction + competing explanations | falsification + study design | Plausible conjecture vs test |
| Product idea, uncertain demand | opportunity map | pretotyping + actual behavior | Validate the right problem |
| Strategic decision | scenario planning | pre-mortem + real options | Sensitivity to future states |
| Feedback and second-order effects | systems map | leverage points and delays | Avoid local optimization |
| Highly uncertain / insufficient data | assumption mapping | cheapest discriminating experiment | Reduce uncertainty first |
| Interpersonal or creative problem | empathy map | lateral stimulus, analogy | Reveal neglected needs |
| Naming/content | wide associative spread | audience filter + phonetic checks | Avoid 20 same-ish names |

## Framing operators

**1. Outcome-neutral HMW.** Convert “We need tool X” to “How might [person] obtain [outcome] under [constraint]?” Test that it does not secretly prescribe X. Generate at least one counterframe where the supposed problem is not real.

**2. JTBD.** For each user: “When [situation], I want to [progress], so I can [result].” State competing jobs, current workarounds, switch costs, and non-users. Do not claim interview evidence without interviews.

**3. Five Whys (with branching).** Ask why a symptom appears; branch rather than forcing one linear cause. Each cause is a hypothesis, not established root truth. Seek measurement to separate branches.

**4. First principles.** Identify physical, legal, logical, economic, and user-imposed constraints. Mark conventions and analogies as optional. Rebuild potential mechanisms from defensible constraints. Beware pretending a guess is fundamental.

**5. Inversion.** Ask how to guarantee the *opposite* outcome, list causes, then reverse those controllable causes. Do not infer symmetry between prevention and creation without evidence.

**6. Counterfactual/zero option.** Imagine no action, delayed action, less action, and removing the goal altogether. Price opportunity and regret costs. “Do nothing” is evaluated as seriously as building.

**7. Boundary shift.** Shift from person to team, team to system, interface to workflow, product to policy, present to future. Generate a solution at each boundary; expose spillovers.

## Expansion operators

**8. SCAMPER, all seven distinct operations:**
- **Substitute:** replace the main mechanism, actor, component, or resource.
- **Combine:** connect two adjacent functions or solutions.
- **Adapt:** borrow an abstract mechanism from a different domain, then examine transfer validity.
- **Modify:** amplify, miniaturize, speed up, slow down, or reconfigure a core dimension.
- **Put to another use:** change beneficiary or context while preserving a mechanism.
- **Eliminate:** remove a step, obligation, object, or assumption entirely.
- **Reverse:** flip direction, ownership, order, incentive, or failure criterion.

**9. Crazy 8s (not literally timed unless user requests).** Quickly generate 8 deliberately distinct rough sketches. Use time pressure as a metaphor, not an invented timer. No editing during generation.

**10. Wild-tail ladder.** Produce conventional → adjacent → radical → absurd. For an absurd proposition, extract the underlying design principle; do not present physical impossibility as viable technology.

**11. Provocation (Po).** State a clearly fictional rule (“No one can enter data”) and mine its implications for automation, better defaults, or avoiding data entry. Mark it fictional. Then reimpose reality constraints.

**12. Random stimulus.** Pick an unrelated object/domain, extract properties, map one onto the problem. Stop if it produces superficial analogies rather than new mechanisms.

**13. Analogical transfer.** Identify source mechanism, target mechanism, and *where the analogy breaks*. An analogy creates candidates, not evidence of performance.

**14. Morphological analysis.** List independent solution dimensions and 2-5 states each, sample meaningful combinations. Before multiplying, remove physically incompatible combinations. High-dimensional matrices can explode; sample deliberately.

**15. TRIZ-style technical contradiction.** State “improving attribute A worsens B.” Explore separation in space, time, condition, scale, or system level; replace assumed tradeoff with an inventive mechanism. Don't claim any proprietary TRIZ database without access.

**16. Biomimicry (optional and bounded).** Identify a desired *function*, find a plausible natural analog, abstract how it works, test whether principles transfer. Biology is not a universal evidence source for human systems.

**17. Concept fan.** Generate several ways of expressing the broader purpose, then multiple mechanisms per purpose; return to the original framing and select cross-branch candidates.

**18. Recombination.** Pair two unlike options, identify real interface/constraint interactions, and build a hybrid with a distinct advantage. Mere stapling together does not count.

**19. Constraint dial.** Remove one constraint to find a novel mechanism; progressively restore it. Repeat for budget, time, capability, privacy, accessibility, and cultural expectations as relevant.

**20. Future-back.** Assume desired end state in 2-5 years, work backward through necessary conditions. Mark conjectural dependencies. Avoid mistaking a narrative for a forecast.

## Perspective and challenge operators

**21. Six Thinking Hats:** White = evidence/data, Red = emotional reaction/intuition (not a fact), Black = risks/objections, Yellow = upside, Green = creative alternatives, Blue = orchestrate/summarize. Use in separate passes, not competing simulated people.

**22. Stakeholder rotation.** Model novice, power user, excluded group, maintainer, regulator, skeptic, funder, and competitor only when relevant. Hypothetical personas are prompts, not interviews or demographic evidence.

**23. Multi-role council.** Assign independent briefs to real subagents when available; otherwise sequentially analyze different criteria and acknowledge shared-model anchoring. Have each role give assumptions, strong case, failure case, and evidence needed. Synthesize agreements and disagreements without averaging away conflicts.

**24. Steelman/opposition.** Make the best defensible case against the favorite and for a real competitor. Distinguish a stronger argument from imaginary opposing evidence.

**25. Pre-mortem.** Assume the chosen path failed in an imaginable future; invent plausible causal explanations, grade likelihood/evidence separately, then design early warning signs and mitigations.

**26. Systems loop map.** Identify stock/flow and reinforcing/balancing loops, delays, externalities, and incentive adaptations. Do not infer precise loop strengths without data.

**27. Opportunity solution tree.** Map desired outcome → opportunities (unmet needs) → multiple solutions → tests. Avoid creating an evidence-free diagram merely for presentation.

**28. Hypothesis tournament.** Write 2-4 mutually distinguishable explanations, predictions under each, evidence that discriminates, and a low-cost observation. Compare against null/base rates.

**29. Causal DAG (conceptual).** Mark plausible arrows, common causes, selection variables, mediators, and reverse directions. A drawn arrow is a proposed causal assumption; observational correlation alone doesn't validate it.

**30. Pretotype/prototype.** Test interest with low-cost mock, fake door (ethically disclosed), concierge, synthetic demonstration, or tiny pilot. Distinguish usability from demand. Define prior success threshold, adequate measurement and informed consent.

**31. Decision sensitivity.** Vary criterion weights, uncertain parameter bounds, baseline forecasts, and risk tolerances. If ranking flips, report contingent decision rather than false certainty.

**32. Real options / reversible action.** For major uncertainty, choose a step that generates information and preserves future choices. Include cost of delay and learning value.

## Candidate record and mechanism map

Do not stop at a name and a pitch. For each candidate that survives the first pass, record:

| Field | Question |
|---|---|
| **Core mechanism** | What is the engine, in 2–4 words? |
| **Distinctive assumption** | What must be true for this candidate but not its rivals? |
| **Origin** | Which technique, analogy, constraint, or observation produced it? |
| **Relevant constraints** | Which hard limits and resource bounds apply? |
| **Relationship** | Twin, hybrid, complement, or independent? |
| **Novel contribution** | What does it add that the existing set lacks, if anything? |
| **Costs / Gives up / Needs** | What does it cost, what does it sacrifice, and what must hold? |

Use the fields as a diagnostic, not a bureaucratic form. A candidate that cannot name a distinct mechanism is probably a cosmetic variation. A candidate that cannot name its distinctive assumption is probably underspecified. A candidate that cannot state a cost is incomplete.

Two candidates sharing a mechanism are twins unless the difference changes the mechanism, the constraints, the user, or the failure mode. Merge exact duplicates; preserve genuine differences. Never merge distinct alternatives merely to make the set look tidy, and never claim the set is exhaustive.

## Stop and saturation conditions

Stop diverging when two consecutive different lenses yield no **mechanically distinct** options *and* the user needs a decision, or when a hard deadline dominates. In DEEP mode explain coverage gaps; do not force arbitrary idea counts. Return to divergence when every finalist depends on the same unverified assumption or when the baseline was never tested.
